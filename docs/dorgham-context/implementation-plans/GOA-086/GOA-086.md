# Implementation Plan — GOA-086: Egyptian applicant visa requirements (structured data + ingestion adapters)

*Revision 2 — incorporates review feedback (adapter contract redesign, dual-write recovery
strategy, FAQ/GOA-045 gap, ingestion_sources decision, auth fix, rate-limit config).*

## Context

GOA-086 is a Sprint-2/backlog **Data** ticket (Service: RAG + Ingestion, P2, 5 points) that adds
Egypt-specific structured visa data to the platform. Today the RAG service only stores visa
content as unstructured `documents` chunks — there is no way to answer precise, factual questions
("what's the minimum blocked-account balance for a German student visa?", "does APS certification
apply to me?") without an LLM guessing from prose. This ticket adds a dedicated `visa_requirements`
table plus 9 Egypt-focused scraper adapters (German Embassy Cairo, APS Cairo, Campus France Egypt,
UK VI Egypt, VFS Global Egypt, Fintiba/Sperrkonto, Czech/Spain/Italy embassies Cairo) so Egyptian
users — the platform's primary demo audience — get accurate, sourced answers to visa questions.

Investigation of the actual codebase (not just the docs) found that **this ticket is partially
scaffolded already**, which materially changes the work:

- Migration `007_add_visa_requirements.sql` **already exists** and creates the table, but it is
  **missing the `egyptian_specific` column** required by the ticket's acceptance criteria. A later
  migration, `008_update_program_requirements.sql`, touches an unrelated table
  (`program_requirements`) — confirmed by reading both files directly, not by trusting the ticket's
  stated filename.
- `POST /internal/visa-requirements` is already routed (`app/api/visa.py` → `app/main.py`) and has
  a Pydantic request schema (`app/schemas/visa.py`), but the service layer
  (`app/services/visa_service.py::upsert_visa_requirements`) is a **literal no-op stub** — it does
  not touch the database at all.
- Unlike `/internal/documents`, the `/internal/visa-requirements` route has **no `X-Internal-Api-Key`
  auth dependency** — confirmed by reading `app/main.py` (no global auth middleware exists; auth is
  applied per-route) and `app/api/visa.py` (no `Security(...)` dependency present).
- 6 of the 9 required adapters do not exist yet (only `IELTSOrgAdapter`, `DAADAdapter`,
  `CheveningAdapter`, `StudyInPolandAdapter`, `StipendiumHungaricumAdapter`, `MastersPortalAdapter`
  exist, none Egypt-specific). Two adapter base classes already exist and match the ticket's stated
  approach exactly: `BaseAdapter` (httpx + BeautifulSoup, for static sites) and
  `BasePlaywrightAdapter` (for JS-heavy sites) — the ticket asks for Playwright only on VFS Global
  Egypt and Fintiba, which lines up with using `BasePlaywrightAdapter` for just those two.
- There is **no `ingestion_sources` database table anywhere in the codebase.** Despite being
  documented in the architecture doc as a config table, the real ingestion pipeline
  (`services/ingestion/handler.py::fetch_all_adapters` and
  `services/ingestion/app/services/run_orchestrator.py::run_ingestion`) simply hardcodes a Python
  list of adapter instances in two places. **Decision (resolved in review): register the 9 adapters
  by adding them to these two hardcoded lists**, matching current practice — building the full
  `ingestion_sources` config-table design is out of scope for this ticket (see Risks).
- The `faq_entries` table exists (migration `005_create_faq_entries.sql`) but is **entirely unused
  by application code** — confirmed by grepping the whole `services/` tree for "faq": only the
  migration file and a doc mention exist. `app/services/rag_service.py::query_rag()` goes straight
  from embedding → pgvector search → Claude call, with no FAQ short-circuit. This is GOA-045's scope
  (unimplemented, no dedicated ticket file). See Dependencies and Questions.
- No `visa_requirements`-specific unit tests exist yet (`services/rag/tests/` has `test_gates.py`,
  `test_query.py`, `test_soft_score.py`; `services/ingestion/tests/test_adapters.py` covers only
  the existing 6 non-Egypt adapters).

The plan below is written against this actual state, not a greenfield assumption.

## Objective

Give the RAG service structured, queryable, Egypt-specific visa data (APS, Sperrkonto/blocked
account, Thanaweya Amma recognition, Egyptian Police Criminal Record Certificate, etc.) sourced
from 9 embassy/visa-centre adapters, exposed both as structured rows (`visa_requirements` table,
for precise Q&A and future profile-matcher gating) and as unstructured `documents` chunks (for
general RAG retrieval), plus curated FAQ entries for the six most common Egypt-specific questions.

## Summary of Requirements (from GOA-086)

1. **Database**: new `visa_requirements` table in `rag_db` — id, country, visa_type, issuing_body,
   source_url, `egyptian_specific`, requirements (JSON), proof_of_funds (JSON), processing_days_min,
   processing_days_max, notes, last_scraped_at, content_hash. Unique key
   `(country, visa_type, issuing_body)`. `proof_of_funds` JSON schema: amount_eur,
   accepted_account_types, blocked_account_providers, minimum_balance_period_days,
   sponsor_letter_accepted, notes_egypt.
2. **9 adapters**: GermanEmbassyCairoAdapter, APSCairoAdapter, CampusFranceEgyptAdapter,
   UKVISAEgyptAdapter, VFSGlobalEgyptAdapter, FintibaSperrkontoAdapter, CzechEmbassyCairoAdapter,
   SpainVisaEgyptAdapter, ItalyEmbassyCairoAdapter.
3. Each adapter run must (a) upsert one or more structured rows into `visa_requirements`, and (b)
   also produce `documents` chunks (existing chunk/embed/upsert pipeline) — both paths, not
   either/or, and a single source page may yield **zero, one, or several** structured visa records.
4. Register all 9 adapters so they run as part of an ingestion pass.
5. `POST /internal/visa-requirements` must actually persist (replace the stub).
6. FAQ seed entries for six Egypt-specific questions (using the existing `faq_entries` table).
7. **Implementation constraints**: httpx+BeautifulSoup for static embassy sites; Playwright only for
   VFS Global Egypt and Fintiba; skip Arabic-only pages gracefully; 2–3s delay between requests;
   retry on HTTP 429/503 with exponential backoff.

## Acceptance Criteria (from ticket, for reference)

- Migration exists to create/complete `visa_requirements` with all listed columns and the unique
  constraint.
- All 9 adapters implemented, each returning structured `Document`-like output.
- Ingestion of a source both upserts `visa_requirements` row(s) and creates `documents` chunks.
- All 9 adapters registered wherever adapters are wired up for a run.
- `POST /internal/visa-requirements` performs a real upsert (not a stub).
- 6 Egypt-specific FAQ entries seeded.
- Unit tests for 7 named adapters (German Embassy, APS, Campus France, Fintiba, Czech, Spain,
  Italy — UK VI Egypt and VFS Global Egypt are not listed under "Unit" in the ticket, only implied
  via "Run all 9 adapters" under Integration).
- Integration tests: run all 9 adapters, verify upsert behavior, verify
  `/internal/visa-requirements`, verify an APS certificate query, verify a blocked-account query,
  verify FAQ cache hit **— blocked on GOA-045's FAQ-check logic existing; see Dependencies below.**

## High-Level Implementation Steps

0. **Re-verify current schema/migration state** (do this at start of implementation, not from this
   plan alone): confirm `app/migrations/` still tops out at `008`, confirm `007`'s
   `visa_requirements` definition still lacks `egyptian_specific`, and confirm no other in-flight
   branch has already added FAQ seeding or the security-module extraction. This plan's file names
   (`009_...`, `010_...`) assume the state observed at planning time.
1. **Close the schema gap.** Add migration `009_add_egyptian_specific_to_visa_requirements.sql`:
   `ALTER TABLE visa_requirements ADD COLUMN egyptian_specific BOOLEAN NOT NULL DEFAULT FALSE;`.
2. **Extract shared auth.** Move `verify_api_key`/`api_key_header` from `app/api/documents.py` into
   `app/core/security.py`; update `documents.py`'s import.
3. **Secure the visa endpoint.** Add `Security(verify_api_key)` to `POST /internal/visa-requirements`
   in `app/api/visa.py`.
4. **Implement the real upsert.** Rewrite `visa_service.upsert_visa_requirements` as an `asyncpg`
   `INSERT ... ON CONFLICT (country, visa_type, issuing_body) DO UPDATE SET ...`, following
   `documents.py`'s transaction pattern. Compare incoming `content_hash` to the stored value; skip
   the write (but still return success) when unchanged, to avoid needless `last_scraped_at` churn.
5. **Extend the visa schema.** Add `egyptian_specific: bool` to `VisaRequirementsRequest`; replace
   the bare `proof_of_funds: Optional[dict]` with a nested model
   (`amount_eur`, `accepted_account_types`, `blocked_account_providers`,
   `minimum_balance_period_days`, `sponsor_letter_accepted`, `notes_egypt`).
6. **Adapter contract — additive, non-breaking.** Do **not** change `scrape()` or
   `extract_documents()`'s signature/return type on `BaseAdapter`/`BasePlaywrightAdapter` — both
   currently return/consume `list[dict]`, and every existing adapter and test
   (`tests/test_adapters.py`) depends on that shape. Instead: for the 9 Egypt adapters only, any
   dict returned by `extract_documents()` **may** include an extra key,
   `"visa_requirements": list[dict]` (0..N structured records extracted from that same page —
   handles the case where one embassy page lists multiple visa sub-types). Non-Egypt adapters never
   set this key; downstream code treats it as `doc_dict.pop("visa_requirements", [])`, so it's a
   no-op for the existing 6 adapters.
7. **Rate limiting.** Add `min_delay`/`max_delay` constructor params to both base adapter classes
   (default 1.0/2.0, matching today's hardcoded `polite_delay()` call — behavior-neutral for
   existing adapters); the 9 Egypt adapters pass `min_delay=2.0, max_delay=3.0` to satisfy the
   ticket's 2–3s requirement.
8. **Build the 9 adapters**, following `daad.py`/`ielts_org.py` conventions (source_name,
   category="visa", country = **destination** country, i.e. Germany/UK/Czech Republic/Spain/
   Italy/France/"Schengen" — not Egypt; Egypt-specific-ness is captured via `egyptian_specific=True`
   on every record these adapters emit, since all 9 sources exist specifically to serve Egyptian
   applicants):
   - 7 static-site adapters on `BaseAdapter`: German Embassy Cairo, APS Cairo, Campus France Egypt,
     UK VI Egypt, Czech Embassy Cairo, Spain Visa Egypt, Italy Embassy Cairo.
   - 2 Playwright adapters on `BasePlaywrightAdapter`: VFS Global Egypt, Fintiba/Sperrkonto.
   - Arabic-page skip: check `<html lang="ar">` / detect predominantly Arabic-script text in
     `extract_documents` and return `[]` gracefully rather than raising.
   - Retry/backoff needs no new code: reuse `fetch_page`/`fetch_binary` from the base classes
     (already wrapped in `with_httpx_backoff` / `with_playwright_backoff`, 429/5xx-aware, exponential
     2–10s) — adapters must call `super().fetch_page()` rather than raw `httpx`/Playwright calls to
     inherit this for free (matches how `DAADAdapter` already does it).
9. **Wire into both ingestion entry points.** In `handler.py::fetch_all_adapters` and
   `run_orchestrator.py::run_ingestion`, add the 9 adapters to the hardcoded lists. In each
   doc-processing loop, `visa_records = doc_dict.pop("visa_requirements", [])` before building the
   `Document`; collect all `visa_records` across the run; for each, call
   `client.upsert_visa_requirement(record)` **independently** of the document chunk/embed/upsert
   path (see dual-write strategy below) — a failure in one must not abort the other.
10. **Dual-write consistency strategy (no 2PC/saga).** The two writes
    (`visa_requirements` row, `documents` chunks) are independently idempotent
    (`(country, visa_type, issuing_body)` unique key on one side, deterministic UUID v5 chunk IDs on
    the other), matching this codebase's existing eventual-consistency tolerance (e.g.
    `local_user_profiles`). Catch and log failures on each path separately — don't let a visa-upsert
    exception abort that page's document upsert or vice versa, mirroring the existing per-adapter
    `asyncio.gather(..., return_exceptions=True)` isolation in `run_orchestrator.py`. Extend the
    completion report/log with `visa_requirements_upserted` / `visa_requirements_failed` counts.
    Recovery is simply re-running the adapter — idempotent upserts on both sides reconcile any
    partial failure without needing distributed-transaction machinery.
11. **Seed the 6 FAQ entries** as `app/migrations/010_seed_egypt_faq_entries.sql` (APS certificate
    necessity, Sperrkonto minimum balance, Thanaweya Amma recognition, Egyptian Police Certificate,
    VFS Global Egypt appointment process, military status certificate), matching the `faq_entries`
    schema (`question_pattern`, `answer_markdown`, `sources` JSONB, `category`). Note: seeding rows
    does not make them reachable at query time — see the GOA-045 gap above.
12. **Tests** — see Testing Strategy.

## Edge Cases to Consider

- **Arabic-only pages**: must skip without throwing — verify against a fixture with `lang="ar"` or
  non-Latin-majority text.
- **Partial data per source**: many embassy pages won't cleanly expose `processing_days_min/max` or
  full `proof_of_funds` — these must remain nullable and not block the upsert.
- **Multiple visa records on one page**: a single embassy page can legitimately describe several
  visa sub-types — `extract_documents` must be able to emit 0, 1, or several
  `visa_requirements` entries per document dict, not assume exactly one.
- **Conflicting upserts within a single run**: the same `(country, visa_type, issuing_body)` key
  scraped twice in one run (e.g. two pages on the same site describing the same visa type) must not
  violate the unique constraint — the `ON CONFLICT DO UPDATE` upsert must be safe to call twice in
  immediate succession with the same key.
- **Partial dual-write failure**: visa-row upsert succeeds but document upsert fails (or vice versa)
  for a given page — handled by independent, idempotent retries on the next run (see step 10), not
  by blocking one path on the other.
- **VFS Global Egypt / Fintiba structure changes**: Playwright-based scraping of JS-heavy sites is
  the most fragile part — needs the same per-adapter isolation already present in
  `run_orchestrator.py` (`return_exceptions=True`) so one broken adapter doesn't fail the whole run.
- **`content_hash` staleness**: compute it consistently (e.g. sha256 of the structured fields, not
  raw HTML) so unchanged pages don't get needlessly re-flagged as updated.
- **Document category value**: `documents.category` CHECK constraint already allows `'visa'` — no
  migration needed there, just confirm adapters set `category="visa"` exactly (case-sensitive).
- **FAQ pattern collisions**: fuzzy matching (`pg_trgm`, threshold 0.85 per the architecture doc) on
  6 new Egypt-specific patterns must not false-positive-match generic non-Egypt visa FAQ text — this
  only matters once GOA-045's matching logic exists to test against.
- **Internal API auth gap**: adding auth to `/internal/visa-requirements` is in-scope, not optional
  — it is currently an unauthenticated write endpoint.
- **Rate-limit override scope**: the new `min_delay`/`max_delay` params must default to the current
  1.0/2.0 values so the 6 existing adapters' behavior and tests are unaffected — only the 9 new
  adapters pass 2.0/3.0.

## Testing Strategy

- **Unit (RAG service)**: `visa_service.upsert_visa_requirements` — insert new row, update existing
  row via conflict (twice in a row, same key, to simulate the within-run duplicate-key edge case),
  verify `egyptian_specific` and JSON fields persist correctly, verify unchanged `content_hash`
  skips the write; schema validation tests for `VisaRequirementsRequest`/`proof_of_funds`; auth test
  asserting `401` without `X-Internal-Api-Key` and `200` with the correct key.
- **Unit (Ingestion — adapters)**: one test per named adapter (German Embassy Cairo, APS Cairo,
  Campus France Egypt, Fintiba, Czech, Spain, Italy) using mocked fixture HTML, following the
  existing `mocker.patch("app.core.robots.robot_checker.is_allowed", ...)` +
  `mocker.patch.object(adapter, "fetch_page", ...)` pattern in `tests/test_adapters.py`. Per
  adapter, assert both: (a) the returned dict(s) shape documents correctly (existing pattern), and
  (b) the `visa_requirements` key is populated with the expected structured fields. Include:
  an Arabic-page-skip test; a malformed/missing-field test (adapter must not crash on partial data,
  optional fields stay `None`); a multi-record-per-page test (one fixture page yielding 2+ visa
  records); a 429-then-success retry test verifying `with_httpx_backoff` retries and eventually
  succeeds (assert call count, not real elapsed time); a rate-limit test asserting `polite_delay` is
  invoked with `(2.0, 3.0)` for an Egypt adapter vs. the default `(1.0, 2.0)` for an existing one
  (assert on call args, not actual sleep duration, to keep tests fast).
- **Integration**: run all 9 adapters against fixtures end-to-end (scrape → chunk → upsert docs +
  upsert visa row(s)); hit `POST /internal/visa-requirements` directly and assert the persisted row;
  exercise a `/query` call that should resolve via the APS certificate content; exercise a query
  that should resolve via blocked-account/Sperrkonto content; a dual-write partial-failure test
  (mock the documents-upsert call to fail while the visa-upsert call succeeds, and assert the run
  continues and reports the failure rather than aborting the adapter/run). **FAQ-cache-hit test is
  descoped from GOA-086's integration suite pending GOA-045** (or implemented as a minimal
  self-contained check if the team decides not to wait — see Questions).
- **Regression**: verify existing 6 adapters and their tests still pass unmodified (particularly
  that adding optional `min_delay`/`max_delay` params and an optional `visa_requirements` key
  doesn't change their existing assertions), and that `documents.category` CHECK constraint and
  existing `/internal/documents` behavior are untouched.

## Risks and Assumptions

- **Resolved assumption**: "Register all 9 adapters in `ingestion_sources`" is implemented as
  additions to the two hardcoded adapter lists (`handler.py`, `run_orchestrator.py`), since no
  `ingestion_sources` DB table exists in this codebase. Flag this wording mismatch to the ticket
  owner — building the actual config table is a separate, larger piece of work if genuinely wanted.
- **Risk**: real embassy/visa-centre websites are external, change frequently, and may block
  scraping (WAF/CAPTCHA), especially Playwright-driven VFS Global Egypt. Tests must not depend on
  live network access; fixtures are required, and live scraping needs manual verification separate
  from CI.
- **Risk**: the ticket lists no actual source URLs for the 9 targets — these must be sourced/
  confirmed before adapters can be written against real markup.
- **Resolved design risk**: the adapter dual-write contract is now additive (an optional
  `visa_requirements` key on existing document dicts), not a breaking change to the shared base
  classes — this removes the earlier risk of inconsistent per-adapter patterns or broken tests.
- **Blocking gap (not a full-ticket blocker)**: the "verify FAQ cache hit" acceptance criterion
  depends on GOA-045's FAQ-check logic, which doesn't exist and isn't a declared dependency. See
  Dependencies section and Questions #1.
- **Assumption**: FAQ seeding is done via a SQL migration (matching how `faq_entries` itself was
  created) rather than a runtime admin-API call, since no `POST /internal/faq` endpoint exists in
  the codebase (only described for the unimplemented GOA-045).
- **`egyptian_specific` semantics**: given the ticket's framing (all 9 sources concern Egyptian
  applicants applying to various destination countries), the working assumption is
  `egyptian_specific=True` for every row these 9 adapters insert, with `country` = destination
  country. Confirm before implementation (Questions #5).
