# Implementation Plan — GOA-088: Structured opportunity ingestion (`program_requirements` and `scholarship_programs`)

*Revision 2 — incorporates repository-review findings (migration renumbering, hidden
`program_requirements` schema work, `notifications_sent`/GOA-024 non-existence, and the
pre-existing no-retry gap on internal RAG upsert calls). This revision does not change GOA-088's
acceptance criteria, its `UNIQUE(provider, name)` key, its `last_scraped_at` idempotency behavior,
its client-side `content_hash` generation strategy, or the GOA-086 dual-write pattern it follows —

## Context

GOA-088 is a Sprint-2/backlog **Data** ticket (Service: Ingestion, P1, 3 points) that gives the
scoring/matching pipeline queryable structured data instead of only unstructured vector chunks.
`program_requirements` (GOA-006) is read today by GOA-012's hard gates, and a new `scholarship_programs`
table is introduced for GOA-024's future diff engine — but nothing in the codebase currently populates
either. GOA-010/GOA-015's adapters emit chunk dicts only; there is no structured extraction path for
university programs or scholarships.

Investigation of the actual codebase (not just the ticket text) found the following, which materially
changes the work relative to a literal reading of the ticket:

- **Migration numbering collision.** The repository's migrations already run through
  `010_seed_egypt_faq_entries.sql` (confirmed by listing `services/rag/app/migrations/`: `001`
  through `010` exist). The ticket's proposed filename, `008_add_scholarship_programs.sql`, collides
  with the already-applied `008_update_program_requirements.sql`. The new migration(s) for GOA-088
  must be numbered `011` (and `012` if split) — **not** `008`. This plan uses `011`/`012` throughout.
- **`program_requirements` cannot support the ticket's upsert/idempotency requirements as it exists
  today.** The ticket's own DDL block only specifies a schema for the *new* table
  (`scholarship_programs`); it says nothing about `program_requirements` needing schema changes, but
  the acceptance criteria still require `POST /internal/program-requirements` to be an idempotent
  upsert "keyed by university + degree_level + country" with idempotency "via content_hash." Reading
  `003_create_program_requirements.sql` and `008_update_program_requirements.sql` directly shows the
  table has **no unique constraint** on `(university, degree_level, country)` and **no `content_hash`,
  `source_url`, `last_scraped_at`, or `updated_at` columns at all** — none of the columns the
  `ON CONFLICT ... DO UPDATE ... WHERE content_hash IS DISTINCT FROM ...` pattern (used by
  `visa_service.py` for GOA-086) needs to exist. This is real, hidden schema work implied by the
  acceptance criteria but not itemized in the ticket's DDL section. It is scoped explicitly in this
  plan (see Task 02) rather than assumed away.
- **`notifications_sent` does not exist anywhere in the repository.** A repository-wide search finds
  zero migrations, models, or application code referencing a `notifications_sent` table — it is
  mentioned only in ticket prose (`all_tickets.md`) as a description of a *future* FK relationship.
  **GOA-088 does not create, alter, or migrate this table.** The ticket's note that
  "`notifications_sent.program_id` should point at `scholarship_programs.id`, not
  `program_requirements.id`" is forward-looking guidance for whichever ticket eventually creates
  `notifications_sent` (likely part of GOA-024 or a dedicated notifications-service ticket), not
  in-scope work here. This plan documents the intended FK for that future ticket's benefit but takes
  no action on it.
- **GOA-024 (Scholarship matcher) does not exist as code.** No ticket detail file, no service, no
  `ScholarshipProgram` model, no diff-engine logic exists anywhere in the repository — only a
  one-line row in the master ticket table and forward-looking prose inside GOA-088's own ticket text.
  **GOA-088's job is limited to preparing the structured data (the `scholarship_programs` table and
  its upsert endpoint) that a future GOA-024 will eventually consume** — this plan does not attempt
  to build any diff-engine or notification-trigger logic, and the "GOA-024 diff query returns rows
  with `last_scraped_at` in the last 24 hours" acceptance-criteria item is satisfied at the SQL level
  only (a query that would work once GOA-024 exists), not by building a GOA-024 service.
- **Internal RAG-upsert HTTP calls have no retry/backoff today.** `services/ingestion/client.py`'s
  existing `upsert_visa_requirement()` and `upsert_chunks()` use a bare synchronous `requests.post(...)`
  with no `tenacity` decorator, unlike the scraping fetches (`fetch_page`/`fetch_binary`), which are
  wrapped in `with_httpx_backoff`/`with_playwright_backoff`. The new `upsert_program_requirement()`
  and `upsert_scholarship_program()` functions this ticket adds will, by direct precedent, follow the
  same no-retry pattern as `upsert_visa_requirement()` — this is treated as **pre-existing technical
  debt, not new work GOA-088 must fix**. It is documented under Future Improvements, not folded into
  any task's Definition of Done.
- **The GOA-086 dual-write pattern is real and directly reusable.** `GermanEmbassyCairoAdapter`
  (`services/ingestion/app/adapters/german_embassy_cairo.py`) already proves the pattern this ticket
  generalizes: a structured record is built alongside the chunk `content` inside the same dict
  returned by `extract_documents()`, tagged under a well-known key (`"visa_requirements"`), popped by
  `run_orchestrator.py` before the LangChain `Document` is constructed, and upserted independently
  with per-record try/except isolation. GOA-088 reuses this mechanism verbatim for two new keys
  (`"program_requirements"`, `"scholarship_programs"`) rather than inventing a new adapter contract.
- **No formal `Document` type exists in ingestion.** Adapters return plain `list[dict]`
  (`{source, category, country, url, content, ...}`); the ticket's "adapters extract structured rows
  in addition to the existing chunked Document output" is accurate in spirit but the "Document" is a
  LangChain `Document` constructed later in the orchestrator, not something adapters emit directly.
  This plan uses "chunk dict" / "document dict" for the existing unstructured output to avoid
  implying a typed class that doesn't exist.
- **Current adapters extract zero structured fields.** `MastersPortalAdapter`, `DAADAdapter`, and
  `CheveningAdapter` (all from GOA-015) currently call `extract_documents()` and return only
  `{source, category, country, url, content}` — no ECTS/GPA/IELTS/deadline/award-amount parsing
  exists anywhere in these three files today. All structured-extraction logic is net-new.

The plan below is written against this actual repository state.

## Objective

Give the RAG service queryable structured rows for university programs (`program_requirements`,
populated by `MastersPortalAdapter`) and scholarships (`scholarship_programs`, populated by
`DAADAdapter`/`CheveningAdapter`), written alongside the existing unstructured chunk pipeline from the
same scrape, following the GOA-086 dual-write pattern exactly, with idempotent upserts via
`content_hash` and a new `goa_ingestion_structured_rows_total{table}` Prometheus counter.

## Summary of Requirements (from GOA-088)

1. **Database**: new `scholarship_programs` table in `rag_db` per the ticket's DDL (id, name,
   provider, country, degree_level, award_amount, deadline, eligibility JSONB, citizenship_eligible,
   min_gpa, min_ielts, source_url, content_hash, last_scraped_at, updated_at; `UNIQUE(provider, name)`).
   A migration (renumbered per the finding above) adds this table to the RAG migration set.
2. **Dual-write extraction**: adapters extract structured rows alongside the existing chunked output,
   from the same scrape (parallel to GOA-086).
3. **`MastersPortalAdapter`** populates `program_requirements` rows: university, country,
   degree_level, min_ects, min_gpa, min_ielts, citizenship_required.
4. **`DAADAdapter`** and **`CheveningAdapter`** populate `scholarship_programs` rows including
   deadline and award_amount.
5. **RAG internal endpoints**: `POST /internal/program-requirements` (upsert, keyed by
   university + degree_level + country) and `POST /internal/scholarship-programs` (upsert, keyed by
   provider + name) — both idempotent via `content_hash`.
6. **Metrics**: `goa_ingestion_structured_rows_total` Prometheus counter, labeled `table`
   (`program_requirements`|`scholarship_programs`).
7. **Existing unstructured `documents` ingestion is unchanged** — this adds the structured path
   alongside it, not in place of it.

## High-Level Architecture

GOA-088 adds a second output channel to the ingestion pipeline, riding the same scrape as the
existing unstructured path:

```
Adapter.scrape() / scrape_structured()      (BaseAdapter / BasePlaywrightAdapter, unchanged ABC)
  └─ fetch_page(url) → html                  (reused, no new fetch for MastersPortal/DAAD)
  └─ extract_documents(html, url) → list[dict]
        each dict: {source, category, country, url, content, <structured_key>: [...]}
                                        │                        │
                                        │                        └─ NEW: structured record(s)
                                        │                           (regex/DOM extraction, each with
                                        │                           its own content_hash)
                                        ▼
run_orchestrator.run_ingestion()
  for doc_dict in adapter_result:
      records = doc_dict.pop("program_requirements", []) or doc_dict.pop("scholarship_programs", [])
      for record in records:
          client.upsert_program_requirement(record)     # POST /internal/program-requirements
          client.upsert_scholarship_program(record)      # POST /internal/scholarship-programs
          → STRUCTURED_ROWS_TOTAL.labels(table=...).inc()
      Document(page_content=doc_dict.pop("content"), metadata=doc_dict)   # unchanged chunk path
                                        │
                                        ▼
RAG service /internal/program-requirements, /internal/scholarship-programs
  FastAPI route → Pydantic validation → Security(verify_api_key) → service layer
                                        │
                                        ▼
Postgres rag_db: program_requirements (upsert on university+degree_level+country)
                 scholarship_programs (upsert on provider+name)
                                        │
                                        ▼
Downstream reads (existing code, unmodified by this ticket):
  - GOA-012 gates.py / scoring.py → SELECT ... FROM program_requirements (real data, not 3 seed rows)
  - GOA-024 (not yet built) → future SELECT ... FROM scholarship_programs WHERE last_scraped_at > now() - interval '24h'
```

**Coexistence with unstructured ingestion**: this is a dual-write, not a replacement. The structured
key is popped off the dict *before* the LangChain `Document` is built, so it never leaks into chunk
metadata, and a structured-write failure can never block a chunk from being embedded — the same
isolation already proven for visa records in `run_orchestrator.py`.

## End-to-End Execution Flow (one ingestion run)

1. `run_ingestion()` starts, instantiates all adapters including `MastersPortalAdapter`,
   `DAADAdapter`, `CheveningAdapter`.
2. `asyncio.gather(*[adapter.scrape() for adapter in adapters], return_exceptions=True)` fetches and
   parses HTML per adapter; each adapter's extraction builds both the chunk `content` string and the
   new structured record(s) from the same parsed DOM — no second HTTP fetch for MastersPortal/DAAD;
   Chevening likely performs one additional fetch for deadline/award data (Task 10).
3. For each adapter's result list, the orchestrator pops `"program_requirements"` or
   `"scholarship_programs"` off each doc dict (whichever applies to that adapter).
4. For each popped record, the orchestrator calls `client.upsert_program_requirement(record)` or
   `client.upsert_scholarship_program(record)`, each wrapped in its own try/except so one bad record
   never blocks the rest of the run; on success, `STRUCTURED_ROWS_TOTAL.labels(table=...).inc()`.
5. The RAG service validates via Pydantic, runs the atomic `INSERT ... ON CONFLICT DO UPDATE` in a
   transaction, returns `{status, id, action}`.
6. Remaining dict fields become a LangChain `Document`, feeding the existing unstructured pipeline
   exactly as today — unaffected by steps 3–5.
7. The run completes; the structured log/report gains `program_requirements_upserted/failed` and
   `scholarship_programs_upserted/failed` counts alongside the existing `visa_requirements_*` counts.
8. Downstream, unrelated to this run: GOA-012's `match_profile`/`get_program_requirements` see real
   rows the next time they query; a future GOA-024 worker would query `scholarship_programs`, but no
   such worker exists yet.

## Edge Cases to Consider

- **Partial/missing structured fields per source**: MastersPortal profile pages, DAAD detail pages,
  and Chevening's pages will not always cleanly state every field (e.g. no explicit ECTS count, no
  parseable deadline) — these must remain nullable and never block the chunk-document write or the
  structured upsert; never fabricate a value the source doesn't state (same principle GOA-086 already
  applies via its `german_embassy_cairo.py` regex extraction).
- **Conflicting upserts within a single run**: the same `(university, degree_level, country)` or
  `(provider, name)` key encountered twice in one run (e.g. two crawled pages describing the same
  program/scholarship) must not violate the unique constraint — the `ON CONFLICT DO UPDATE` upsert
  must be safe to call twice in immediate succession with the same key.
- **Partial dual-write failure**: a structured-row upsert fails while the chunk-document write for the
  same page succeeds (or vice versa) — handled by independent, idempotent retries on the next
  scheduled ingestion run, not by blocking one path on the other (same as GOA-086).
- **`content_hash` staleness**: computed consistently over the normalized structured fields (not raw
  HTML), so unchanged source pages don't get needlessly re-flagged as updated on every run.
- **Existing `program_requirements` seed rows**: the 3 hand-seeded rows from
  `008_update_program_requirements.sql` (TU Munich/Germany/Master, ETH Zurich/Switzerland/Master,
  Erasmus Mundus/Europe/Master) must not collide when the new unique constraint is added — verified
  distinct on `(university, degree_level, country)` already, but Task 02 must confirm this before
  applying the constraint in any environment with additional manually-inserted rows.
- **Chevening's current target page doesn't carry deadline/award data**: the adapter's only configured
  URL today is an eligibility page — satisfying the ticket's unit-test acceptance criterion likely
  requires fetching a second page (see Task 11).

  counted, chunk document for that source still produced; malformed/partial structured record → 422
  at the RAG boundary, ingestion logs and continues without crashing the adapter's whole batch;
  unparseable `deadline` → stored as `NULL`, not rejected (see Task 04's validator decision).
