Inter-Service Communication Patterns

Sync REST Call
Used when Service A needs data from Service B to complete the current request. Example: Orchestration calls GET /users/:id/subscription to check tier before routing. Creates a runtime dependency — if B is down, A is degraded. Use sparingly; cache results in Redis.
Async SQS Event
Used when Service A produces something Service B should react to, but A doesn't need to wait. Example: Scholarship Matcher publishes ScholarshipMatched event; Notification service picks it up independently. Fully decoupled — neither service knows about the other's database.
Local Snapshot
RAG service subscribes to UserUpdated events and maintains a local read-optimised copy of profile fields it needs for scoring. Avoids synchronous calls on every scoring request. Slightly eventually consistent — acceptable for profile matching.
Never do this
Service A directly queries Service B's database. This creates tight coupling — schema changes in B break A silently, deployments must be coordinated, and the database becomes a shared bottleneck. One PostgreSQL instance with separate schemas is fine; cross-schema queries are not.

Application Scoring System

The Profile Matcher uses a 3-stage hybrid scoring pipeline. Hard gates eliminate ineligible programs instantly (score = 0). Soft weighted scoring ranks eligible programs. An LLM contextual boost adjusts for CV quality and narrative fit.

Stage 1 — Hard Gates (Deterministic, Zero Token Cost)

Run as pure TypeScript/Python boolean checks before any LLM is involved. If any gate fails, the pipeline stops immediately and returns score: 0 with a specific blockedBy reason. No further processing.

GateCheckFixable?
ECTS Creditsuser.ects ≥ program.min_ectsYes — take more courses
Degree Leveluser.degree_level ∈ program.accepted_degreesYes — complete degree first
Citizenshipuser.citizenship ∈ program.eligible_citizenshipsRarely
Age limituser.age ≤ program.max_age (if set)No
Prerequisitesrequired_subjects ⊆ user.completed_subjectsYes

Stage 2 — Weighted Soft Score (Deterministic, Zero Token Cost)

Each factor is normalised to 0–100 and multiplied by its weight. Weights are configurable per program type — a research master's weights GPA and publications higher; a professional master's weights work experience higher.

FactorWeightNormalisation
GPA / Grade30%Scale to 0–100 based on program's grading system
IELTS Band25%(band / 9) × 100
Work / Research Experience25%Years → 0–100 via sigmoid curve
Extracurriculars / Publications20%0–100 based on quantity + quality heuristic

Stage 3 — LLM Contextual Boost (−10 to +10)

The only stage that uses an LLM. The Profile Matcher agent reads the full CV and SOP and returns a single integer adjustment with a brief justification. The ±10 range is intentional: it can influence borderline cases but cannot override a clear structural mismatch. Uses Claude Haiku to keep cost low (~$0.002 per scoring call).

When boost is positive (+3 to +10)
Strong research trajectory despite mediocre GPA. Publications in directly relevant field. Unique interdisciplinary background that matches program's stated mission. Compelling personal statement with specific fit reasoning.
When boost is negative (−3 to −10)
CV is generic with no clear motivation. Background is completely unrelated to the program field. Personal statement contains red flags (gaps, contradictions). Skills listed don't align with program requirements.

Final Score Formula

final_score = min(100, max(0, round(stage2_weighted_sum + stage3_boost))) Example: Stage 1: PASS (all gates cleared) Stage 2: GPA=72×0.30 + IELTS=78×0.25 + EXP=50×0.25 + EXTRA=40×0.20 = 21.6 + 19.5 + 12.5 + 8.0 = 61.6 Stage 3: LLM boost = +5 (strong research fit) Final: round(61.6 + 5) = 67 → "Moderate match"

Important Design Decision

Never expose sub-scores to the user — only the final confidence score and the gap list. Showing sub-scores invites gaming ("I'll add fake work experience to raise that factor"). The gap list tells them what to actually fix, not how the score was calculated.

Key Decisions & Tips

Critical decisions made during architecture, with the reasoning behind each. Read this before starting implementation to avoid common pitfalls.

Architecture Decisions

⚠ Speaking latency is your biggest risk
The 3-second P95 target with WebSocket + STT + 4 agents + TTS is tight. The fix is streaming: start sending ElevenLabs TTS audio as LLM tokens arrive — don't wait for the full response. Use Anthropic's streaming API and pipe tokens to TTS with a 20-token buffer. Test this in Week 1, not Week 3. If you discover a latency problem in Week 3, you don't have time to fix it.
⚠ DevOps tax will eat your sprint time
Managing 8 services, 5 CI/CD pipelines, and AWS deployments is a lot of work. Mitigate by: (1) one developer owns all infra and sets up docker-compose.yml on Day 1, (2) the golden rule: if it runs in docker-compose locally, it runs on ECS — same images, (3) don't touch AWS in Week 1 at all.
✓ Skip the live MCP scraper
Most university and visa requirements don't change week to week. A weekly scheduled re-scrape into the vector DB is the right architecture. Live on-demand scraping adds latency, fragility (sites go down), and complexity for no real benefit. The one place MCP could add value is a single check_scholarship_deadlines tool querying your own PostgreSQL — not scraping external sites.
✓ Database-per-service enforcement
Use one PostgreSQL instance with separate schemas per service (not 8 separate RDS instances). Enforce the ownership rule in code: no service imports another service's schema types or queries another service's tables. This gives you architectural correctness without the operational cost of 8 RDS instances.
Go for Speaking and Gateway only
Go is genuinely excellent for the Speaking service (WebSocket concurrency, 2KB per goroutine vs Node's event loop overhead) and Gateway (high-throughput routing, no AI libraries). Don't extend Go to services that depend on the Python AI ecosystem — you'd lose LangChain, sentence-transformers, and pdfplumber for no benefit.
✓ Orchestration moved to Python
LangChain Python is significantly more mature than LangChain.js — gets new agent features first, better documentation, larger community. All AI services (Orchestration, RAG, Writing) now share one language, eliminating JS/Python context switching for developers owning the AI layer. Pydantic models replace TypeScript interfaces for SQS event validation.
Notifications are eventual, not real-time
The scholarship notification system is about telling users "Chevening 2026 applications are now open" at the right moment — not live data. Design it as a diff engine: after each weekly scrape, compare new scholarships against user profiles, publish match events to SQS. This is simpler, cheaper, and more reliable than live scraping, and more useful than real-time data.

Scoring System Tips

Never show sub-scores to users
Only show the final confidence score and the gap list. Showing individual factor scores invites gaming. The gap list tells users what to fix; they don't need to know the weights to act on it.
Hard gates are cheap — run them first
Stage 1 is pure boolean logic: zero tokens, zero cost, microsecond execution. Always run hard gates before any LLM call. If ECTS fails, don't waste a Haiku call on the boost. This also means you can score thousands of programs against a user profile in a batch operation cheaply.
LLM boost ceiling is intentional
The ±10 ceiling means the LLM boost can swing a 65 to a 75 (moderate → strong) but cannot turn a 40 into an 80. This is correct — a brilliant CV doesn't overcome a genuinely weak academic profile. The LLM adjusts for things the structured data misses; it doesn't override it.
Cache scoring aggressively
Cache score results in Redis for 1 hour keyed by score:{userId}:{programId}. A user's profile doesn't change minute-to-minute. This avoids redundant LLM boost calls when a user views the same program multiple times in a session.

Why REST and Not RPC (gRPC) for Inter-Service Communication

A common question for microservices. Here is the full reasoning for this project specifically.

The case for REST (why we chose it)
Three languages, one protocol. Go, TypeScript, and Python all have first-class HTTP clients with zero setup. Adding gRPC requires protobuf toolchain, code generation step, and generated stubs in every language — that is three separate build pipelines to maintain in a 4-week project.

SSE and WebSocket are already in play. The Speaking service uses WebSocket and the Orchestration service streams via SSE. Both are HTTP-native. gRPC streaming (server-streaming, bidirectional) is a different protocol and cannot share the same ALB listener without special configuration.

AWS ALB speaks HTTP natively. ALB routes and health-checks HTTP/1.1 and HTTP/2 out of the box. gRPC requires HTTP/2 with specific ALB target group settings and h2c support per service — more Terraform surface area.

Debugging is trivial. Every REST call is inspectable with curl, Postman, or browser DevTools. gRPC requires grpcurl or a dedicated client. During a 4-week sprint where debugging speed matters, this is a real cost.

LangChain and AI SDKs are HTTP-native. Anthropic, OpenAI, ElevenLabs — every AI SDK makes HTTP calls. Your services are thin wrappers around those calls. Adding a gRPC transport layer on top of HTTP calls adds no value.
When gRPC would have been the right choice
High-frequency internal calls at scale. If the Orchestration service called the RAG service 500 times per second, gRPC's binary encoding (protobuf) and persistent HTTP/2 connections would reduce latency and bandwidth meaningfully. At your traffic levels, the difference is microseconds.

Strict schema enforcement across many teams. Protobuf schemas are a contract enforced at compile time — impossible to send a malformed message. With 5 developers and Pydantic/TypeScript types already doing validation, this is handled.

Polyglot teams at scale. At Netflix or Uber scale with 50+ services and dozens of teams, a single .proto file as the contract is invaluable. At 8 services and 5 developers, the overhead outweighs the benefit.

The rule of thumb: use gRPC when you have high call frequency between services you fully control, and REST when you have varied transports, external integrations, or a small team that needs to move fast.
What you get instead of schema enforcement: the /packages/contracts directory holds Pydantic models (Python) and TypeScript interfaces that validate every SQS event and internal API payload. This gives you 95% of protobuf's safety with zero toolchain overhead.

Common Pitfalls to Avoid

Don't start on AWS directly
Always develop locally first. AWS debugging is slow — logs are in CloudWatch, deploys take minutes, and you're burning money while debugging. Docker Compose locally means instant feedback. Only Youssef (infra lead) touches AWS in Week 1.
Don't build all 11 agents at once
Sprint 1: get the Supervisor routing to one working downstream service. Sprint 2: add remaining agents. A working 3-agent system you can demo is better than a broken 11-agent system you can't.
Watch AI API costs during development
Set Langfuse up in Week 1 (not Week 4). Token costs during development can spike unexpectedly, especially during load testing. Set per-user daily limits early. Claude Haiku for free-tier features saves 15–20× vs Sonnet.
Don't use localStorage in browser
Store JWTs in httpOnly cookies (set by the Gateway). Never in localStorage — it's vulnerable to XSS. Session state belongs on the server (Redis), not the client.

Full IELTS exam simulation across all 4 skills — Academic and General Training. Reading and Listening use static grading with no AI. Speaking and Writing use the existing AI evaluation swarms. Content sourced from Cambridge IELTS books 11–18.

Exam Types

Academic
For students applying to undergraduate or postgraduate programmes. Reading uses complex academic texts. Task 1 Writing requires describing graphs, charts, or diagrams. Speaking topics tend toward abstract discussion.
General Training
For work experience, secondary education, or migration purposes. Reading uses workplace and social texts. Task 1 Writing is a formal or informal letter. Same Speaking and Listening format as Academic.

Why Reading and Listening Have No AI

Deterministic correctness
Reading and Listening have official answer keys. Grading is binary — the answer is right or wrong. An LLM adds no value here and introduces inconsistency. The exact match grader is 100% accurate, instant, and costs zero tokens.
Cost and latency
Reading grading: pure Python, under 100ms P95, zero API cost. Listening grading: identical. Running 40 answers through an LLM would cost ~$0.05 per exam and take 5–10 seconds for no accuracy benefit.
Honest feedback
The answer key never lies. The official IELTS band conversion tables are public. Users get the exact score a real IELTS test would give them — not an approximation.

Speaking Exam — Part Structure

Part 1 — Interview (4–5 questions, ~4 min)
General questions about familiar topics (home, work, studies, interests). One question at a time, examiner-style. Same format Academic and General Training.
Part 2 — Long Turn (1 min prep + 2 min speaking)
Cue card with topic and 3–4 bullet points. 60-second silent preparation period. Then 2 minutes of uninterrupted speaking. Server enforces both timers.
Part 3 — Discussion (4–5 questions, ~5 min)
Abstract discussion questions related to Part 2 topic. Tests ability to discuss ideas and opinions at length.

Writing Exam — Task Structure

Academic Task 1 (min 150 words, 20 min recommended)
Describe a graph, chart, table, or diagram. Stimulus image delivered from S3 via pre-signed URL. Evaluated by Writing swarm for Task Achievement, Coherence, Vocabulary, Grammar. Weight: 33% of Writing band.
General Training Task 1 (min 150 words, 20 min recommended)
Write a formal or semi-formal letter. Letter scenario delivered as text. Same 4-agent evaluation. Weight: 33%.
Task 2 (min 250 words, 40 min recommended)
Essay responding to a point of view, argument, or problem. Same format for Academic and General Training. Weight: 67% of Writing band. Same 4-agent evaluation.

Key Architecture Rules

Services NEVER query another service's database directly. All cross-service data access goes through REST calls (sync, when result needed immediately) or SQS events (async, when decoupling is possible). The Exam service never touches writing_db. The RAG service never touches user_db. Violating this creates hidden coupling that breaks independently-deployable services.
The Exam service is the single source of truth for all exam state, question banks, and results. The Speaking and Writing services handle evaluation only — they call back to the Exam service to store results. This keeps exam orchestration logic in one place.

User Workflow

A complete walkthrough of every interaction a user has with the Global Opportunity Assistant — from the moment they land on the homepage to receiving a scholarship notification months later. Every step maps to a specific service, API call, and ticket in the implementation plan.

Phase 0 — Discovery & Landing

The user arrives at https://goa.app via Google, a referral, or a university notice board. They have not yet created an account.

What the user sees
A landing page explaining the platform — opportunity matching, IELTS preparation, CV review. A prominent Get Started Free button and a See how it works section. No login wall on the landing page itself.
What happens technically
CloudFront serves the static Next.js bundle from S3. The landing page makes zero API calls — it is fully static. Route 53 resolves the domain. WAF inspects the request before it reaches CloudFront.

Phase 1 — Registration & Onboarding

Step 1 — Register
User clicks Get Started Free, lands on /register. Fills in name, email, password. Clicks Create Account.

Behind the scenes: Frontend sends POST /api/auth/register → Gateway → User service. Gateway calls User service POST /users. User service validates email uniqueness, bcrypt-hashes the password, creates the user record in user_db with subscriptionTier = free. Gateway generates a signed JWT (1h expiry) and a refresh token. JWT stored in an httpOnly cookie — never in localStorage. User service publishes a UserCreated event to SQS (future: welcome email).
Step 2 — Profile Setup Wizard
After registration, the user is redirected to a 4-step onboarding wizard at /onboarding. This is not mandatory but unlocks personalised matching immediately.

Step 2a — Academic background: Degree level (Bachelor/Master/None), field of study, GPA (numeric), ECTS credits completed, graduation year.

Step 2b — Language: IELTS overall band (if taken), individual skill bands (Reading/Listening/Speaking/Writing). If not taken yet, they select "Planning to take IELTS" — the platform will suggest starting with a practice exam.

Step 2c — Targets: Target countries (multi-select: UK, Germany, Italy, Canada, etc.), opportunity type (Masters study / Work / Both), field of interest.

Step 2d — CV upload (optional): Drag-and-drop a PDF or Word CV. If uploaded, a CVUploaded event is published to SQS — the CV Processor Lambda picks it up asynchronously, extracts text and structured data (name, degree, skills, experience), and stores it in writing_db. The user does not wait for this — they proceed to the dashboard while extraction runs in the background.

Behind the scenes: Each wizard step sends PUT /api/users/:id/profile → Gateway → User service. User service updates user_profiles table, then publishes a UserUpdated event to SQS. RAG service consumes this event and updates its local profile snapshot used for scoring.
Step 3 — Dashboard First Load
User lands on /chat — the main interface. On first load, the Orchestration service is called with an implicit OPPORTUNITY_SEARCH intent based on the profile just created. The Supervisor Agent routes to the RAG service's POST /match endpoint, which runs the 3-stage scoring pipeline against all programs in the database. The top 5 matches are shown as cards in the chat response alongside a welcome message. This happens in under 3 seconds on first load.

Phase 2 — Free Tier Usage

The free tier includes: RAG-powered Q&A, opportunity search, and application checklists. No speaking, writing evaluation, or CV review until the user upgrades.

Scenario A — Asking an IELTS question
User types: "What IELTS score do I need for a Master's in Computer Science in Germany?"

Flow: POST /api/chat → Gateway (checks JWT, rate limit: 20 RAG queries/hour free tier) → Orchestration service. Supervisor Agent classifies intent as RAG (confidence 0.97). Langfuse root trace created with user_id, session_id, intent.

Orchestration calls RAG service POST /query with the question. RAG service embeds the question using text-embedding-3-small, performs cosine similarity search against pgvector, retrieves top 5 chunks from ingested DAAD and university pages. Claude Haiku generates an answer grounded in the retrieved content. Answer streamed back to client via SSE — tokens appear as they are generated. Langfuse logs: model=haiku, input_tokens=820, output_tokens=310, latency=1.4s, cost=$0.002.

What the user sees: A conversational answer with specific IELTS requirements for German CS programs, citing the universities the information was retrieved from. Sources listed below the answer.
Scenario B — Browsing opportunity matches
User types: "Show me universities in Italy I can apply to" or navigates to /profile → Opportunities tab.

Flow: Supervisor Agent classifies intent as OPPORTUNITY_SEARCH. Orchestration calls RAG service POST /match with the user's profile snapshot. Profile Matcher runs:

  → Stage 1 (hard gates): checks ECTS, degree level, citizenship for each Italian program. Programs failing any gate get score=0 and are filtered out with a reason label ("ECTS insufficient").

  → Stage 2 (soft scoring): GPA×0.30 + IELTS×0.25 + experience×0.25 + extracurriculars×0.20 for all programs that passed Stage 1.

  → Stage 3 (LLM boost): a single Claude Haiku call reads the CV text and returns ±10 integer adjustment per program. Runs only for programs with Stage 2 score > 50 (not worth boosting low scorers).

Results returned as a ranked list. User sees opportunity cards with colour-coded confidence scores (green ≥80, amber 60-79, red <60), program name, university, country, deadline, and a "View requirements" button.

Clicking a blocked card: Shows the specific gate that failed ("Your ECTS credits (150) are below the minimum required (180)") with a "Can I fix this?" flag. Gives the user actionable information rather than just hiding the program.
Scenario C — Generating an application checklist
User clicks Get Checklist on an opportunity card for the University of Padua Computer Engineering program.

Flow: GET /api/opportunities/:programId/checklist?userId=:id → Gateway → RAG service. RAG service generates a personalised checklist by comparing the program's requirements against the user's profile gaps. Items grouped by phase: Language Prep → Documents → Application → Post-acceptance.

What the user sees: An interactive checklist. Each item shows: what to do, estimated days, whether it is blocked by an incomplete dependency, and links to official resources. This is the core free-tier value — it is a complete personalised action plan for one specific program. The user can check items off and they are persisted. Free users can generate checklists for up to 3 programs.

Phase 3 — Discovering the Upgrade Prompt

Hitting a paid feature wall
User types: "Can you review my CV?" or clicks Start Speaking Practice.

Flow: Gateway checks subscriptionTier from Redis cache (populated from User service). Tier = free. Gateway returns 403 with {"error": "subscription_required", "feature": "cv_review", "upgradeUrl": "/pricing"}.

What the user sees: A modal explaining what they get with paid access — CV review, Speaking practice, Writing evaluation, full exam simulations. A clear list of what remains free. A Upgrade for $7/month button. The modal is not aggressive — it appears inline in the chat, not as a full-page takeover.
Completing payment via Stripe
User clicks Upgrade → navigated to /pricing → clicks Subscribe.

Flow: Frontend calls POST /api/billing/create-checkout. Next.js API route creates a Stripe Checkout session and redirects the user to Stripe's hosted payment page. User enters card details on Stripe (PCI compliant — GOA never sees card data). On success, Stripe sends a webhook to POST /api/billing/webhook. The webhook handler verifies the Stripe signature, then calls User service PATCH /users/:id/subscription with tier=paid. User service updates the DB and publishes a UserUpdated event. Gateway's Redis cache for this user is invalidated — next request will re-fetch the paid tier.

What the user sees: A Stripe payment page, then a redirect back to /chat?upgraded=true showing a confirmation banner. All paid features immediately unlocked.

Phase 4 — Paid Feature Usage

CV Review
User uploads their CV to the chat (drag-and-drop or click to upload). Or types: "Review my CV for a software engineering role in Germany."

If CV already uploaded during onboarding: Orchestration retrieves the already-extracted CV text from writing_db — no re-upload needed.

If new CV uploaded: File sent to POST /api/cv/upload → Writing service → stored in S3 → GPT-4V or pdfplumber extracts text → stored in writing_db.

Evaluation flow: Orchestration routes to Writing service POST /cv/review with {userId, cvS3Key, targetCountry: "Germany", targetField: "Software Engineering"}. Writing service calls RAG service for German CV conventions (photo required? Lebenslauf format?). Claude Sonnet analyses the CV across: structure/formatting, skills gaps for target field, ATS keyword optimisation, length, country-specific conventions.

Response streamed back via SSE — sections appear as they are generated. Each section shows a score (0-100), specific issues found, and exact suggested rewrites. The user can ask follow-up questions: "Rewrite my summary section" → Orchestration routes back to Writing service with the specific rewrite request.

What the user sees: Colour-coded section scores, specific feedback per section, and a "Rewrite this section" button per section that triggers a targeted improvement.
Speaking Practice (non-exam)
User clicks Start Speaking Practice or types: "I want to practice IELTS speaking."

Flow: Supervisor Agent classifies as SPEAKING. Orchestration returns a WebSocket upgrade URL to the frontend. Gateway proxies the WebSocket connection to the Speaking service. A speaking session record is created in speaking_db.

Real-time audio pipeline:
  1. Frontend requests microphone permission via browser MediaRecorder API
  2. Audio chunks (PCM 16kHz mono) streamed over WebSocket to Speaking service
  3. Voice activity detection: silence > 1.5s triggers transcription
  4. Speaking service sends audio to ElevenLabs STT API → transcript returned in <1.5s
  5. 4 agent goroutines launch in parallel (Fluency, Lexical, Grammar, Pronunciation) — each receives the transcript and the original question prompt
  6. As the first agent tokens arrive, ElevenLabs TTS streaming begins — audio starts playing before all agents have finished
  7. Full evaluation result sent back via WebSocket: {overall_band, per_criterion_bands, feedback, transcript}

Latency target: First TTS audio reaches client in under 3 seconds from end of speaking (P95). SLO violation logged if exceeded.

What the user sees: Waveform visualiser during recording, live transcript appearing as they speak, then spoken feedback from the AI examiner with colour-coded criterion scores.
Writing Practice (non-exam)
User types their essay directly into the chat text area or the dedicated Writing practice interface.

Evaluation flow: 4 Writing agents run concurrently via asyncio.gather — Task Response, Cohesion, Vocabulary, Grammar. Each returns a band score, feedback, and inline_issues (character-level annotations marking specific problems in the text). Overall band = mean of 4 criteria rounded to nearest 0.5.

What the user sees: The essay displayed with colour-coded highlights — red for grammar issues, blue for vocabulary, orange for cohesion, purple for task response. Hovering a highlight shows the specific issue and a suggested improvement. Overall band score at the top. A "Show improved version" button (paid) that generates a rewritten version at one band higher.

Phase 5 — IELTS Exam Preparation

The user navigates to /exam. They see the exam prep dashboard with 4 skill cards (Reading, Listening, Speaking, Writing) and an Academic/General Training toggle. Their last score is shown on each card if they have taken exams before.

Reading Exam — Full Walkthrough
User selects Academic, clicks Start Reading Exam.

Flow: GET /api/exam/reading/start?examType=academic → Gateway (validates paid tier, rate-limits: max 3 exams/hour) → Exam service. Exam service selects a random unseen Academic Reading test from exam_db (Cambridge IELTS 14-18, tests the user has not attempted before). Returns: 3 passages with full text, 40 questions (mix of MC, TFNG, fill-blank, matching, short-answer), session_id, timer=3600 seconds. Answer key is stored server-side only — never sent to client.

During the exam: User reads passages on the left panel, answers questions on the right. Question navigation sidebar shows answered (filled circle) vs unanswered (empty circle). User can highlight passage text for personal reference. Timer counts down in the top-right corner. Frontend sends a heartbeat PATCH /api/exam/sessions/:id/heartbeat every 60 seconds to keep the session alive. If the user refreshes the page, sessionStorage restores the session and re-fetches remaining time from the server.

On submit: PUT /api/exam/reading/:sessionId/submit with all 40 answers. Exam service grades in pure Python in under 100ms: exact-match case-insensitive for fill-blank and short-answer, option match for MC, TRUE/FALSE/NOT GIVEN for TFNG. Raw score (e.g. 32/40) converted to IELTS band (e.g. 7.5) using the official Academic Reading band conversion table seeded in exam_db.

Results page: Band score prominently displayed. Section breakdown (Section 1: 13/13, Section 2: 11/14, Section 3: 8/13). Per-question view with user answer vs correct answer (green/red). Question type breakdown: "You scored 95% on Multiple Choice but 62% on True/False/Not Given — consider practising this type." A "Practise TFNG" button links back to /exam with the question type pre-filtered.
Listening Exam — Full Walkthrough
User clicks Start Listening Exam.

Flow: Exam service generates 4 pre-signed S3 URLs for the audio files (sections 1-4), each valid for 2 hours. A session record is created with time_limit=2400 seconds (40 minutes). The pre-signed URLs are unique to this session — they cannot be shared or used in a different session.

During the exam: Custom HTML5 audio player with seeking disabled — the progress bar is display-only. User cannot skip ahead (mirroring real IELTS conditions). Section 1 audio plays. Questions for Section 1 are displayed alongside the audio. A 30-second silence gap appears between sections (shown as a countdown). User answers questions while listening. A scratch-pad is available for notes (not submitted). After all 4 sections, a 10-minute answer transfer period allows editing answers before final submission.

On submit: Same grading logic as Reading. Official Listening band conversion table (different from Reading) used. Results identical format to Reading.
Speaking Exam — Full Walkthrough
User clicks Start Speaking Exam.

Flow: Exam service creates a speaking exam session with questions sourced from Cambridge IELTS books: 4 Part 1 questions, 1 Part 2 cue card (topic + 3 bullet points), 4 Part 3 discussion questions. Session stored in exam_db.

Part 1 (Interview, ~4 min): Questions displayed one at a time. User clicks Record Answer, speaks their response, clicks Next Question. No score or feedback shown — only a neutral confirmation. Transcript stored silently after each answer.

Part 2 (Long Turn, ~3 min): Cue card displayed prominently. A 60-second preparation timer starts automatically — user takes notes, recording is paused. When the timer ends, the 120-second speaking timer begins. User delivers their long turn. Transcript stored silently.

Part 3 (Discussion, ~5 min): 4 discussion questions related to the Part 2 topic. Same format as Part 1. After the final answer, user clicks Submit Exam.

Holistic evaluation: Exam service sends all 3 parts' transcripts + prompts to Speaking service POST /evaluate/holistic. 4 agents run in parallel with the full context — each agent sees all 3 transcripts but evaluates only its criterion. The evaluation spinner shows: "Analysing your performance across all 3 parts..." This takes 5-8 seconds.

Results page: Overall band. 4 criterion cards, each with: band score, overall feedback paragraph, Part 1/2/3 tabs showing per-part narrative ("Your fluency was strong in Parts 1 and 3 but degraded noticeably under time pressure in Part 2"), specific transcript quotes with issue annotations ("In Part 2 you said 'I think... umm... the technology is very... important' — this hesitation pattern dropped your Fluency band from 7 to 6"), and 1 concrete improvement tip per criterion.
Writing Exam — Full Walkthrough
User selects Academic, clicks Start Writing Exam.

Flow: Exam service returns: Task 1 prompt (a bar chart comparing energy consumption) + the chart image as a pre-signed S3 URL, Task 2 essay prompt ("Some people think that environmental problems are too big for individuals to solve..."), session timer = 3600 seconds.

Phase 6 — Progress Tracking & Personalisation

Exam history and score trends
After completing several exams, the user navigates to /profile → Exam Progress tab.

What the user sees: Line chart per skill showing last 10 exam bands over time (e.g. Reading: 5.5, 6.0, 6.0, 6.5, 7.0 — clear improvement trend). Weak areas panel: one card per skill showing the specific lowest-scoring section or criterion ("Reading: Section 3 — True/False/Not Given: 54%"). An overall estimated IELTS band computed as the average of the last exam per skill, with a disclaimer that this is based on practice exams.

Estimated band used for matching: Once the user has real exam data, the Orchestration service pulls it via the Exam service's internal profile endpoint. The RAG service's scoring pipeline uses the real measured IELTS bands (e.g. Reading: 7.0, Listening: 7.5, Speaking: 6.5, Writing: 6.0) instead of the self-reported score from onboarding. This makes opportunity matching significantly more accurate.
Personalised chat recommendations
User returns to /chat after completing exams. Types: "What should I focus on to get into Padua?"

What happens: Orchestration calls Exam service for the user's profile summary: {reading_band: 7.0, listening_band: 7.5, speaking_band: 6.5, writing_band: 6.0, weak_area: "Writing — Task Achievement", last_exam_date: "2026-05-15"}. This is injected into the Supervisor's context.

The Supervisor also checks Padua's requirements via RAG (min IELTS 6.5 overall, no sub-band below 6.0 for Computer Engineering). It detects that the user's Writing band of 6.0 is exactly at the minimum — a risk factor. It routes to a personalised response: "Your Reading and Listening are strong for Padua (7.0 and 7.5 vs their minimum 6.5). Your main risk is Writing — you scored 6.0 in your last practice exam, which is at Padua's minimum. Your weakest sub-criterion is Task Achievement, meaning your essays are not fully addressing the prompt. I recommend practising Task 2 with timed conditions 3 times per week. Would you like to start a Writing practice session now?"

This level of specificity is only possible because the system has the user's real exam data, the program's requirements, and the connection between them.

Phase 7 — Scholarship Notifications (Async, Background)

The weekly ingestion cycle
Every Sunday at 02:00 UTC, EventBridge triggers the Ingestion Worker Lambda. It scrapes configured official sources (Mastersportal, DAAD, Chevening, Erasmus+, gov visa portals), chunks updated content, re-embeds only changed documents (content hash comparison), and upserts into pgvector. The ingestion report is written to S3.

Immediately after ingestion, EventBridge triggers the Scholarship Matcher Lambda. It queries the RAG DB for programs updated in the last 24 hours. For each updated program, it runs Stage 1 (hard gates only — fast and cheap) against all user profiles with matching targetCountry. If score > 0 (eligible) and the program has a deadline within 90 days and the user has not been notified this cycle: a ScholarshipMatched SQS event is published.
The user receives a notification
The Notification Lambda consumes the ScholarshipMatched event from SQS. It renders an email template with: scholarship name, deadline, match reason ("You meet the eligibility requirements for Computer Engineering at TU Munich — deadline March 15th"), and a direct link to view the full checklist on GOA.

The email is sent via AWS SES from notifications@goa.app. An in-app notification record is also created in notification_db — the user sees a notification badge on their next visit.

What the user experiences: They receive an email: "Ahmed, Chevening Scholarship applications for 2027/28 are now open. Based on your profile, you are eligible. Deadline: November 7th 2026." They click the link, land on the GOA checklist for Chevening, and begin their application with 4 months to go rather than discovering it the week before the deadline closes.

Database Schema Designs

Every service owns its database exclusively — no cross-service SQL queries. Each schema is shown with full DDL, table explanations, and relationship rationale. Services reference other services' data only via UUID fields, never via foreign key constraints across database boundaries.

1. Gateway Service — gateway_redis (Redis)

The Gateway is stateless by design. It uses Redis exclusively as a fast ephemeral store — no PostgreSQL. All keys have TTLs and are never considered source of truth.

Key patternTypeTTLPurpose
rl:user:{userId}:{route}:{minute}Counter (INCR)60sSliding-window rate limiter. Incremented on every request, expired after 1 minute. Gateway returns 429 when count exceeds threshold.
sub:{userId}String300sSubscription tier cache. Populated on first request by calling User service. Avoids a User service call on every request. On subscription change, User service publishes UserUpdated — Gateway invalidates this key.
jti:{jti}StringRemaining token lifetimeJWT access token blacklist. On logout, the token's JWT ID is stored here. Gateway checks this set on every request to catch tokens used after logout before they naturally expire.
exam_owner:{sessionId}String (userId)300sExam session ownership cache. Prevents one user submitting another user's exam answers. Checked on every exam submit and result endpoint.
cb:{service}String ("open")60sCircuit breaker state. Key exists = circuit is open (service degraded). Expires automatically to allow recovery. Gateway writes this on 3 consecutive failures.
exam_start:{userId}:{hour}Counter3600sExam session rate limit. Max 3 exam starts per user per hour. Prevents question bank farming.
Redis is not a substitute for a database — it is a cache and ephemeral counter store. None of these keys are the authoritative source of any piece of data. If Redis is flushed, all keys are rebuilt from scratch as requests come in. This is intentional.

The Exam service has the largest schema in the system. Cross-Cutting Schema Design Decisions

UUID PKs everywhere — no integer sequences
All tables use uuid_generate_v4() as the primary key. This enables IDs to be generated before insert (useful for idempotent operations and event-driven flows), prevents enumeration attacks (sequential IDs expose record counts), and makes cross-service ID references safe even if two services independently generate IDs.
No FK constraints across service boundaries
speaking_sessions.user_id is a plain UUID column — not REFERENCES user_db.users. Cross-service FK constraints couple database deployments: you cannot deploy the Speaking service without the User service being live first. Consistency is maintained at the application layer via SQS events and API calls, not database constraints.
JSONB for evolving AI outputs
Agent evaluation results (agent_responses, inline_issues, section_scores) are stored as JSONB. The schema of LLM outputs will evolve — adding part_notes or improvement_tip to the Speaking agent should not require a schema migration. JSONB also supports GIN indexing if query patterns emerge later.
Partial indices for hot query paths
WHERE clause on index definitions targets only the rows that queries actually touch. idx_rt_user_active (WHERE revoked_at IS NULL) means the refresh token lookup only scans active tokens. idx_es_status (WHERE status = 'in_progress') means the session expiry job only scans active sessions. These stay small even as the tables grow.
IVFFlat vs HNSW for pgvector
The documents table uses IVFFlat with lists=100. At 200-500 documents IVFFlat is overkill — exact search would work fine. IVFFlat is chosen to ensure the index behaves correctly as the corpus grows to thousands of documents without a migration. HNSW would give slightly better recall but uses more memory (relevant only at tens of thousands of vectors).
Band conversion tables in DB not code
IELTS occasionally revises its band conversion tables. Storing them in exam_db means corrections are data migrations, not code deploys. Seeded at startup from a fixture file in the repository under version control. The band_conversion_tables table uses a composite PK of (skill_area, exam_type, raw_score) — no UUID needed, the natural key is the primary key.
